# إدارة الخطط والاشتراكات — قبول التنفيذ

التاريخ: 15 أكتوبر 2026. النطاق حصريًا `Pertomax EG`، قاعدة Supabase المرجع `msvgzsfzrqlrfpstthhe`، ومستودع `pertomaxeg-svg/petro-web`.

## ما يعمل على قاعدة Supabase بعد التطبيق

- طُبقت `0008`, `0010`, `0011` ثم `0012` على المرجع المحدد؛ سجل الترحيل والبصمات ونتيجة postflight في `docs/PLATFORM-USER-ADMIN-ROLLOUT.md` و`docs/FINANCE-CORE-ACCEPTANCE.md`. المخطط لم يعد معطلاً، وAPI الكتالوج تستدعي RPCs v2 الفعلية.
- تعريف الخطط، المسودات، تعديل المسودة، إصدار نسخة جديدة، النشر/الجدولة، وإيقاف استقبال خطط جديدة متصل بقاعدة Supabase. يمكن تعديل سعر الخطة ضمن حدود التحقق، مع أسعار البداية من الإعدادات الافتراضية. نسخ الشروط المنشورة لا تتغير عند تعديل الخطة أو إعداداتها.
- واجهة RTL تجمع القائمة الجانبية وأقسام الإدارة في نظام موحد. تبويبات الباقات تعرض الكتالوج، الأسعار، المميزات/الحقوق، تاريخ النسخ، والسعر المخصص. بحث الجداول وفلاترها وترتيبها وصفحاتها تعمل على السجلات الفعلية؛ تفاصيل النسخ تعرض المقارنة والسعر والحقوق والحالة وتاريخ السريان.
- تخصيص السعر يحفظ الجهة أو فرعها، الخطة، البداية/النهاية، السبب، المعتمد من جلسة المالك، الأولوية، السعر القياسي والخاص، وسجل السعر السابق؛ يرفض الخادم فرعًا لا يتبع الجهة المختارة والتعارض والتكرار. لا يسمح بتخصيص المحطات.
- إعداد الأسعار الافتراضية محفوظ على Supabase: الشركات 500/750/1000 ج.م لكل مركبة سنويًا كقيم بداية قابلة للتعديل، ومقدم الخدمة 5000 ج.م لكل فرع سنويًا، والمحطات صفر بلا عمولة أو رسوم غسيل. NFC بقيمة 100 ج.م في إعداد مستقل عن سعر الخطة والاشتراك؛ لا تنشأ رسوم ضريبة أو تركيب أو استبدال أو خصم ترقية نسبي.
- يبدأ الإصدار بحقوق وإعدادات فارغة. لا تُعامل النصوص التاريخية كحقوق معتمدة، ولا يمكن نشر إصدار بلا البنود المعتمدة المطلوبة. لم يُنشأ أو يُنشر أي سجل خطة أو تخصيص فعلي للاختبار.
- في كود الإدارة تُنشأ طلبات الاشتراك/التجديد/تغيير الخطة وتُراجع مع حفظ نسخة الخطة والسعر والحقوق والنطاق والتواريخ. لم تُنشأ طلبات أو اشتراكات فعلية على قاعدة Supabase. أضيفت نواة الدفتر والإيصالات في 0012 ويمكن ربط قبض الاشتراك بالطلب، لكن التسجيل لا يضيف رصيد خدمات ولا يفعّل اشتراكًا مدفوعًا قبل اعتماد سياسة المحاسبة والتغطية المطلوبة. لا يُعدّ مرفق الإثبات قبضًا، ولا توجد محفظة أو إيرادات مصطنعة.
- انتهاء الاشتراك وسلامة نطاق الفرع موصوفان ومختبران في دوال قاعدة البيانات المعزولة. لا توجد حتى الآن نقاط إنشاء خدمة موصولة كلها ببوابة المنع؛ لذلك لا ندّعي منع كل خدمة جديدة من العمل بعد الانتهاء. انتهاء فرع مقدم لا يوقف فروع الجهة الأخرى في اختبار النطاق.

## الاعتمادات التي تمنع التفعيل المدفوع أو إثبات التغطية

- توجد نواة مالية وإيصالات في 0012، لكن إعداد محاسبة الاشتراك الافتراضي لا يجيز تفعيلًا مدفوعًا أو تسجيل إيراد قبل اعتماد سياسة المحاسبة والتسوية وربط التغطية. لا يُعد إثبات مرفق قبضًا، ولا تُنشأ محفظة مقابل الاشتراك.
- لا يوجد سجل أسطول مركبات معتمد لإثبات تغطية الشركة حسب عدد المركبات. لا يُنشأ أسطول أو مركبات وهمية. تسجيل سعر الخطة وتحريرها لا يعتمد تغطية فعلية.
- خيارات حقوق/ميزات الخطط قابلة للإعداد، لكن لا تُقدَّم كميزات إنتاجية حتى يحددها المالك ويعتمدها صراحةً. لا توجد تعرفة ترقية نسبية أو ضرائب أو تركيب أو استبدال في النظام.
- دالة السماح بخدمات جديدة حسب اشتراك الفرع غير موصولة بكل نقاط إنشاء الخدمات. يلزم تكامل أمامي واختبار لكل خدمة تعتمد على الاشتراك قبل ادعاء فرض الانتهاء على مستوى المنتج.
- RPCs v1 القديمة `petro_billing_admin_create_plan` و`petro_billing_admin_add_plan_version` تقيّد أسعارها بالجدول الافتراضي؛ مسارات API الحالية تستدعي v2 القابلة للتحرير. لم نجد في مصدر التطبيق المحلي مستهلكًا آخر لـv1 خارج اختبارات SQL. لا نستنتج من ذلك عدم وجود مستهلك خارجي، ولا نغيّر grants أو نزيل دوالًا قديمة ضمن هذه الحزمة.

## الاختبارات والتصميم

- `bash lib/db/rebuild/run-local-test.sh` نجح على PostgreSQL مؤقت، مع API محلية، وغطى المسودات والتعديل والنشر والتعارض والتكرار وعزل الجهات والفروع والأسعار الخاصة وحقوق/لقطات الإصدارات وحالات الطلبات والمحطات المجانية، إضافة إلى دفتر المالية والشحن والإيصالات والتحويل والتكرار والتزامن والعكس ومنع تفعيل مدفوع بلا قبض. لا ينشئ الاختبار أي سجلات مالية في Supabase الحية.
- نجح فحص أنواع الويب وAPI، وبناء الويب وAPI، وفحص ACL الحي وdry-run بعد التطبيق. API المعاينة استجابت لـ`/api/healthz` بـHTTP 200.
- اختُبر هيكل الإدارة والقائمة الجانبية بصريًا في sandbox معزول عند 1280×900 و402×874؛ العينة الاصطناعية موسومة بوضوح ومفصولة عن API والقاعدة، وليست إثباتًا لبيانات التطبيق أو جلسة محمية. الشاشة المالية في التطبيق تتطلب جلسة مخولة؛ لم تتوفر جلسة مالية مصرح بها للمتصفح، ولم نضف تجاوز مصادقة أو نعدل حسابًا حقيقيًا.
- استُخدمت مراجعة تصميم مخصصة، ومكونات/توكنات Pertomax الحالية، وقواعد RTL الصريحة؛ لم يُغيّر إطار العمل ولم تُخلط مكتبات واجهات. مراجع shadcn وCarbon الرسمية لم تكن متاحة في المحاولة السابقة، فلا ندّعي الاطلاع المباشر عليها. المهارات `ui-ux-pro-max`, `web-design-guidelines`, و`vercel-react-best-practices` غير مثبتة ولم نثبتها من مصدر خارجي.

## القبول المتبقي

1. ربط القبض بمصدر مالي موثوق قبل تفعيل اشتراك مدفوع أو تسجيل إيراد.
2. اعتماد سجل أسطول وربط تغطية الشركات به، دون إنشاء مركبات اختبار في بيانات حقيقية.
3. اعتماد حقوق/مزايا كل خطة وربط بوابة انتهاء الاشتراك بجميع نقاط إنشاء الخدمات المعتمدة عليه.
4. التحقق من الواجهات المحمية بجلسة مالك مصرح بها؛ لم تتوفر جلسة اختبار مصرح بها في المتصفح، ولا يجوز تجاوز تسجيل الدخول أو تعديل الحسابات الحقيقية للاختبار.

لا يُطبّق 0009 ضمن الحزمة، ولا تُسحب صلاحية `petro_set_account_status(uuid,text)` القديمة.
