# الإدارة المركزية: مستخدمو المنصة والباقات

- النطاق محصور في Pertomax EG وقاعدة Supabase `msvgzsfzrqlrfpstthhe` ومستودع `pertomaxeg-svg/petro-web`. لم يُفحص مشروع آخر أو يُغيّر اتصال أو Secret أو بيانات حساب/جهة.
- نجح اختبار PostgreSQL المعزول وHTTP للـAPI، ثم طُبقت 0008 و0010 و0011 فقط بعد مطابقة الشروط. بقي 0009 مؤجلًا، ولم تُنشأ خطط منشورة أو تخصيصات سعر أو طلبات أو اشتراكات أو مدفوعات حية.

## معنى «قاعدة مشتركة» وما أمكن إثباته

المعاينة المهيأة تحتوي workflow واحدًا لخادم API وworkflow للويب، وكلاهما يعمل من شجرة التطوير نفسها. مسارات الإدارة في API الحالية تستدعي RPCs v2 من 0011؛ لا توجد في مصدر API الحالي إحالة إلى RPCs v1 الأقدم، وتظهر إحالات v1 في اختبارات SQL فقط. هذا يصف المستهلكين المعروفين داخل هذا المستودع، ولا يثبت أن نسخة ثانية من API أو خدمة خارجية لا تستخدم القاعدة. لم يُفحص أي مشروع أو اتصال آخر، ولا يجوز افتراض وجود مستهلك خارجي أو عدمه. يظل معنى «المشتركة» غير محسوم من أدلة المشروع المتاحة؛ يبقى 0009 مؤجلًا وحذف صلاحية RPC القديم خارج هذه الحزمة.

## تفسير فرق ACL

القياس القديم `24` نطاقًا حيًا مقابل `6` محليًا لم يكن تعارض مورد أو امتياز؛ الـfixture المحلي القديم أغفل 18 نطاقًا تديرها Supabase. أُعيد بناء الاختبار محليًا لمطابقة المالك والمخطط ونوع المورد والدور والامتياز وخيار المنح:

- `postgres`: `public` و`storage`، لكل من sequences/functions/tables.
- `supabase_admin`: `extensions`, `graphql`, `graphql_public`, `public`, `realtime`، لكل نوع مورد.
- `supabase_auth_admin`: `auth`، لكل نوع مورد.

في `public`, `storage`, `graphql`, `graphql_public` يمنح الدور الافتراضي الصلاحيات للأدوار `anon`, `authenticated`, `postgres`, `service_role`. `extensions` خاص بـ`postgres` مع `GRANT OPTION`. في `realtime` و`auth` الأدوار `dashboard_user` و`postgres`؛ و`postgres` في جداول `realtime` لديه `GRANT OPTION` فقط على `SELECT` و`INSERT`. قارنت إعادة البناء المصححة كل هذه الصفوف، لا العدد وحده. بصمة الصفوف القانونية التي يستخدمها dry-run هي `65e09b76b80628c531e6e223128f0a201befefeb9eaa75685dae5dafdc337cea`. اختبارات الترحيل أثبتت أن 0008 و0010 و0011 لا تغير هذه ACLs.

## انتقال 0008 ومسار الرجوع

- 0008 يضيف دليل المستخدمين والتفاصيل وRPCs لتغيير الأدوار والحالة مع سبب إلزامي، ويبقي `petro_set_account_status(uuid,text)` وتعريفها وبصمتها `d6a0defdb1102d00b0743723db453bad` ومنحها لـ`authenticated` و`service_role` والمالك دون `anon`.
- اختبار معزول غطى رفض السبب المفقود والتغيير الذاتي، حماية آخر مالك، منع التصعيد، صلاحيات المالك، وتوافق المسار القديم. يلزم تسجيل دخول مالك مخول لاختبار الواجهة الحية؛ لا يوجد تجاوز دخول أو حساب اختبار حي.
- 0009 مؤجل. لا يزيل `EXECUTE` من RPC القديم في هذه الحزمة.
- خطة الرجوع حُفظت قبل التطبيق في `docs/ADMIN-CENTRAL-MIGRATION-ROLLBACK.md`: الترحيلات بمعاملات مستقلة، وأي رجوع تشغيلي يكون بتبديل API مع إبقاء المخطط والسجل والتدقيق؛ لا يوجد حذف عكسي تلقائي.
- `0010` يهيئ النسخ القديمة كمسودات (`draft`) بلا حقوق/إعدادات معتمدة؛ لا تُعامل تلقائيًا كخطط منشورة. `0011` يضيف صف إعدادات الأسعار الوحيد بالقيم المعتمدة؛ لا ينشئ خطة أو اشتراكًا.

## نتيجة التطبيق الحي

نجح التطبيق وpostflight على المرجع `msvgzsfzrqlrfpstthhe`. قارَن المشغل كل 24 نطاقًا من `pg_default_acl` بحسب المالك والمخطط ونوع المورد والدور والامتياز وخيار المنح، لا العدد وحده. تطابقت البصمة قبل/بعد `65e09b76b80628c531e6e223128f0a201befefeb9eaa75685dae5dafdc337cea`؛ وكان اختلاف 24 حيًا مقابل 6 في fixture سابق نقصًا في 18 نطاقًا يديرها Supabase، لا تعارض ACL يمس شروط الترحيل.

بعد التطبيق بقي تعريف ومنح `petro_set_account_status(uuid,text)` القديم دون تغيير (بصمة `d6a0defdb1102d00b0743723db453bad`؛ `EXECUTE` لـ`authenticated` و`service_role` والمالك، وليس `anon`). لم يُسجّل 0009. بقيت حسابات المستخدمين والجهات وعضوياتها دون تعديل. 0010 أضاف بيانات النسخ الوصفية الافتراضية كمسودات، و0011 أضاف صف إعدادات التسعير؛ لم ينشأ سجل خطة أو سعر خاص أو طلب/اشتراك/تحصيل حقيقي.
