تاريخ العمل: 15 أكتوبر 2026. النطاق: `Pertomax EG` فقط، مستودع `pertomaxeg-svg/petro-web` وقاعدة Supabase `msvgzsfzrqlrfpstthhe`. هذا سجل التنفيذ والاختبار لهذه المرحلة، وليس مواصفة منتج أصلية.

## المراجع والحدود

- `docs/PERTOMAX-EG-ENGINEERING-REFERENCE-v3.md` هو المرجع الهندسي الذي قدمه المستخدم، وليس دليلاً على اكتمال التنفيذ.
- `PERTOMAX-CENTRAL-ADMIN-GAPS.md` مصفوفة فجوات أنشئت من مراجعة الكود والبنية؛ ليست PRD أصليًا.
- لا توجد مواصفة أصلية منفصلة وجدتها لدورة طلبات انضمام الجهات، أو لوحات الأطراف، أو البنوك والمستندات والتحديثات المعتمدة. لا تنشئ هذه المرحلة هذه المسارات ولا تستنتج تفاصيل مالية أو قانونية إلزامية.
- تُحفظ قيم الحالة منفصلة: `approval_status` للاعتماد (`pending`, `approved`) و`operational_status` للتشغيل (`inactive`, `active`, `suspended`). لا يوجد مسار رفض طلب مستقل في البنية الحالية؛ السجل المعلق ليس بديلاً عن سير طلب تسجيل كامل. يبقى `status` القديم للتوافق، ولا تعتمد عليه الواجهة الجديدة لاتخاذ قرار الاعتماد.
- الإنشاء يبدأ `pending/inactive`. الاعتماد لا يفعّل الجهة أو الفرع تلقائيًا. لا يسمح بالتفعيل قبل الاعتماد. لا يوجد حذف ولا تغيير لتاريخ مالي. لا تتضمن المرحلة محافظًا أو اشتراكات أو مركبات أو كتـالوجًا أو مخزونًا أو تطبيقات عمال.
- كود الجهة فريد على مستوى المنصة، وكود الفرع فريد داخل الجهة. ربط الفرع يُفرض في قاعدة البيانات وفي API، لا في عناصر الواجهة فقط.

## مسار الترقية الآمن

1. لقاعدة اختبار فارغة: تطبيق `current-schema.sql` كـbaseline ثم fixture الاختبار المحلي لـ`auth.users`، ثم `0004` مرة واحدة، ثم `0005_central_organizations_branches.sql`.
2. لقاعدة الإنتاج الحالية: لا baseline ولا `0001`–`0004`. يُفحص أولاً مشروع Supabase، TLS، بصمات 0004، قيود/RLS والامتيازات المتأثرة، وعدم وجود أعمدة 0005 أو تطبيق جزئي. عند أي اختلاف يتوقف المسار.
3. عند تطابق الشروط فقط يُنفذ `0005` كوحدة ذرية. لا يكتب أي إصدار إلى سجل Supabase ولا يغير `DEFAULT ACL` أو RLS. الإجراء الجديد لا يشغل ترحيلات سابقة تلقائيًا؛ 0004 يبقى حالة مطبقة غير مسجلة.
4. التراجع الآمن الأول هو الرجوع إلى إصدار التطبيق السابق مع إبقاء الأعمدة الإضافية والبيانات كما هي. لا تُحذف أعمدة 0005 آليًا؛ إزالة المخطط تتطلب نسخة بيانات وموافقة منفصلة.

## نتيجة مهمة المستندات والبنوك والطلبات

أُضيفت المتطلبات المفتوحة لنفس قسم الجهات والفروع، وطُبق 0006 سابقًا ثم 0007 لاستكمال مقدم الطلب المؤكد بلا عضوية. لم يُعد تطبيق baseline أو 0004–0006، ولم يُكتب سجل تاريخي مصطنع. مخطط ما بعد 0007 طابق البنية المحلية المختبرة؛ نتائج التطبيق وحدود الاختبار في `docs/AUTH-02-0007-SELF-SERVICE.md`. يبقى اختبار جلسة المستخدم المصادق ورفع/تنزيل ملف فعلي على Storage؛ لا تعتبر صور بوابة الدخول أو ردود HTTP العامة إثباتًا لواجهة الإدارة الداخلية.

إفادة المستخدم بأن تجربة الجهات والفروع السابقة تعمل طبيعية سجلت كاختبار أبلغ به المستخدم، وليست فحصًا آليًا أجريته.

صور المعاينة الحالية للصفحة العامة غير المسجلة حُدثت على سطح المكتب والهاتف؛ مسارات التطوير في هذه الجلسة تخدم فرع `pertomax-central-orgs-20261015`، بينما بقيت إعدادات الإنتاج دون تغيير.

## إدارة مستخدمي المنصة — 0008/0009

أضيف دليل حقيقي لحسابات المنصة مع بحث وصفحات وفلاتر حالة/دور، ملف حساب وسجل تدقيق منقح، وإدارة أدوار المنصة وحالة الحساب مع سبب إلزامي. فصل أدوار المنصة عن عضويات الجهات محفوظ في الواجهة وقيود الخادم؛ لا تعرض الواجهة بريد Auth أو بيانات اعتماد. جميع وظائف الإدارة الجديدة مقيدة بدور مالك المنصة، مع منع التغيير الذاتي وحماية الحساب غير النشط.

نجح اختبار SQL وإعادة البناء المحليان على PostgreSQL مؤقت، وكذلك اختبار HTTP لمسارات API الفعلية مع RPCs 0008/0009 وقاعدة محلية وناقل Supabase وهمي محصور. يشمل ذلك البحث والصفحات والفلاتر، الحالة والتدقيق، رفض الجلسة غير المسجلة، العمليات، والتغيير الذاتي. فحوص النوع والبناء للخادم والويب و`mockup-sandbox` نجحت؛ لم تُختبر واجهة مالك مسجلة لأن أداة المعاينة لا تملك جلسة دخول.

لم يطبق 0008 أو 0009 على قاعدة Supabase الحية، ولم تُغيّر بيانات أو أسرار أو اتصالات. فصل 0008 الإضافي عن 0009 الذي يسحب صلاحية RPC القديم ضروري لأن نسخة `origin/main` الحالية ما زالت تستخدم `petro_set_account_status(uuid,text)` دون سبب. خطة الإصدار والرجوع وجرد الاعتماد موجودة في `docs/PLATFORM-USER-ADMIN-ROLLOUT.md`. لم يُؤكد وجود مستهلك خارجي آخر؛ يجب التحقق من ذلك ضمن مشروع Pertomax EG قبل 0009.
